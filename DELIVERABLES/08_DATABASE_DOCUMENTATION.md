## 1. Design principles

### 1.1 Portability

The schema is deliberately portable across SQL Server, Postgres and MySQL:

- **No database enums.** Constrained values are strings validated against
  `VisionCartConstants.cs`.
- **No arrays.**
- **No native JSON columns.** JSON is a stringified `nvarchar`.

The cost is that the database will not reject an invalid status; the application
does. The benefit is that the schema moves.

### 1.2 Identifiers

Every primary key is a **`Cuid`** — a 25-character, time-ordered, collision-
resistant string.

| Property | Consequence |
| --- | --- |
| Time-ordered | New rows append to the clustered index; no page-split fragmentation |
| String | Legacy identifiers stayed valid through the migration |
| Opaque | Safe in a URL — no sequence to enumerate, no information leaked |

Identity child tables are narrowed to 30 characters because SQL Server refused
the default key length combination (error 1753).

### 1.3 Money

**24 columns** end in `Minor` and every one is an `int` holding minor units
(paisa). The model builder throws if any is declared otherwise, so the invariant
cannot be broken by a future migration. Pinned by `SchemaMigrationTests`.

## 3. Relationships and delete behaviour

38 foreign keys. The delete behaviour carries real meaning:

| Behaviour | Count | Meaning |
| --- | --- | --- |
| `CASCADE` | 17 | Children of an owned aggregate — order lines with their order |
| `NO_ACTION` / `RESTRICT` | 15 | **Protective** — the delete is refused |
| `SET_NULL` | 6 | The reference is optional; history survives the referent |

### 3.1 Protective relationships worth naming

| Relationship | Behaviour | Why |
| --- | --- | --- |
| `OrderItem.PrescriptionId` → `Prescription` | **Restrict** | A prescription used by an order cannot be deleted. Pinned by test, using raw SQL — EF's client-side fixup would otherwise null the FK and issue an UPDATE before the DELETE, hiding the constraint. |
| `Address.UserId` → `AspNetUsers` | No action | Past orders reference the address they shipped to |
| `CartItem.VariantId` → `FrameVariant` | No action | A variant in a live basket cannot vanish |
| `AuditLog.UserId` → `AspNetUsers` | Set null | The trail outlives the account, deliberately |

> **Migration note.** SQL Server's single-cascade-path rule forced seven
> relationships away from cascade. Each demotion **strengthened** an invariant
> rather than weakening it — the database now refuses deletes the application
> already refused.

## 4. Indexes

97 non-primary-key indexes.

### 4.1 Filtered unique indexes

Six indexes carry a filter. These reproduce nullable-unique semantics: a column
that must be unique **when present** but may be null many times.

```sql
CREATE UNIQUE INDEX [IX_...] ON [...] ([Column]) WHERE [Column] IS NOT NULL;
```

Without the filter, SQL Server would treat two nulls as duplicates and reject the
second row.

### 4.2 Load-bearing unique constraints

`SchemaMigrationTests.Unique_constraints_from_the_prisma_schema_survive` asserts
10 unique constraints survived the migration — including patient file number,
frame slug, variant SKU, order number and promotion code.

## 5. Seed data

`DatabaseSeeder` runs on start and is **idempotent**. It creates:

| Data | Detail |
| --- | --- |
| Roles | Customer, Staff, Optician, Admin |
| Administrator | Only if `Seed:AdminEmail` and `Seed:AdminPassword` are configured |
| Optician | Same condition |
| Brands, categories | Reference data |
| Frames | 10 frames, 30 colourways |
| Lens options | Types, indices, coatings, tints |
| Shipping rates | Delivery pricing |
| Settings | Store defaults |

**Staff passwords come from configuration, never from a literal in the seeder.**
The legacy seed shipped published demo passwords; the production guard now
rejects them outright.

## 6. Migrations

One migration, `InitialCreate`, which builds all 36 tables.

Applied **automatically on application start** — a deliberate choice, because
shared hosting offers no command line from which to run `dotnet ef database
update`.

Migrations in this project are **additive**: no migration drops a column. That is
what makes the rollback procedure in `09_DEPLOYMENT_DOCUMENT.md` §10 safe, since
an older build runs against a newer schema. Preserve the property.

## 7. Creating the database

Three routes, in order of preference:

**1. Let the application do it.** Point `ConnectionStrings__DefaultConnection` at
an empty database and start the app. Tables are created, migrated and seeded.

**2. Run the script.** `database/01_schema.sql` is idempotent — safe to run
against an empty or partly-migrated database.

```bash
sqlcmd -S <server> -d <database> -i 01_schema.sql
```

**3. EF tooling** (developer machines):

```bash
dotnet ef database update --project src/VisionCart.Infrastructure \
                          --startup-project src/VisionCart.Infrastructure
```

## 8. Backup

> **A database backup on its own is not a backup.**
>
> `wwwroot/uploads` holds every product photograph and try-on overlay, and those
> files are referenced by `MediaAsset` rows. Restoring the database without the
> uploads folder gives you a catalogue of broken images.
>
> Back up both together, and confirm periodically that you can restore them.

## 9. Not verified

- **Production database sizing and growth rates** — no production instance exists
  to measure.
- **Index effectiveness under production load** — the indexes are those the EF
  model declares; no query-plan analysis was performed against realistic volumes.

  been tested.
