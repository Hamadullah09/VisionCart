# VisionCart — prescription eyewear store

An online optical shop: customers browse frames, try them on with their own
photo or live camera, enter a prescription, and order lenses made to it. Staff
run the whole practice from a back office — catalogue, stock, images, patient
records, prescriptions, orders, the lab queue and promotions.

Built with Next.js 16 (App Router), TypeScript, Tailwind v4 and Prisma.

## The virtual try-on

The feature the shop is built around, and the part worth understanding.

**How it works.** A frame overlay is a transparent PNG plus two *anchors* —
normalised coordinates marking where the wearer's pupils should sit inside that
artwork. Given the customer's two pupils, exactly one similarity transform
(uniform scale, rotation, translation) puts the anchors on the pupils. That is
the entire placement algorithm; there is no per-face tuning and no guesswork.

**Finding the pupils.** MediaPipe's face landmarker runs *in the customer's
browser*. The model (~3.7 MB) and its WebAssembly runtime are served from
`/public`, not a CDN, so no third party ever sees a customer's face and the shop
keeps working if Google's CDN is blocked.

**Measuring PD.** The visible iris is 11.7 mm across in almost every adult, so
it works as a ruler: pupil distance in pixels × 11.7 ÷ iris diameter in pixels
gives millimetres. Expect ±2 mm. The app reports a confidence score, refuses
implausible values, and always tells the customer an optician will confirm it.

**When detection isn't available** — an old browser, a missing model file, a
photo it can't read — the customer drags two markers onto their own eyes and
everything downstream is identical. The feature degrades, it never breaks.

**Privacy.** Photos and camera frames never leave the browser. The only image
that reaches the server is a composited snapshot the customer explicitly saves
— and that is **off by default**. Turn on *Settings → Virtual try-on → Let
customers save try-on snapshots* if you want them kept on the patient file;
with it off the save route refuses uploads outright, not just hides the button.
Customers can always download their own image either way.

### Adding artwork for a real frame

1. **Frames → pick a frame → a colourway → Virtual try-on tab.**
2. Upload a front-on PNG with a transparent background, temples pointing out.
3. Drag the **L** and **R** markers onto the centre of each lens.
4. Check the live preview on the reference face, then **Save calibration**.

Colourways without artwork simply don't appear in the mirror; the frame page
warns you which ones are missing.

The placeholder artwork in `/public/frames` is generated by
`npm run frames:generate` — it exists so a fresh install has a working shop
before any photography happens. Replace it frame by frame.

| Screen         | What it's for                                                          |
| -------------- | ---------------------------------------------------------------------- |
| **Dashboard**  | Today's orders, money taken, prescriptions waiting, low stock           |
| **Orders**     | Lab ticket per line, payment, refunds, shipping, status                 |
| **Patients**   | Files, prescriptions, verification, documents, order history            |
| **Frames**     | Catalogue, colourways, stock, photos, try-on calibration                |
| **Media**      | Drag-and-drop bulk image upload                                         |
| **Lenses**     | The lens builder's steps, options and prices                            |
| **Promotions** | Deals and codes — live the moment you save                              |
| **Import**     | CSV in and out                                                          |
| **Settings**   | Store details, selling rules, try-on switches                           |

### Uploading images

Drop a whole shoot onto **Media**, or onto a specific colourway from the frame
page. Files upload one at a time with per-file progress; a corrupt file is
reported by name and the rest still go through. Every image is auto-rotated
from EXIF, capped at 2000 px, converted to WebP and thumbnailed. Try-on
overlays stay PNG so they keep their transparency.

### CSV import and export

Exports are round-trippable: export **Frames & stock**, edit prices in Excel,
import the same file back. Rows are matched on `variant_sku` (frames) or
`file_no` (patients), so re-importing updates rather than duplicates.

Import always runs a **check** first, listing bad rows by line number. Nothing
is written until you press *Import for real*.

### Promotions

Six kinds: percentage off, fixed amount off, free shipping, BOGO, free lens
upgrade, and bundle price. Each can be limited by spend, quantity, brand,
collection, date window, total uses, uses per customer, and first-orders-only.

The highest-priority offer always applies. Others join it only if every
promotion in play is marked **stackable** — so a headline deal never silently
doubles up, but a shipping perk can ride alongside a discount code.

## Payments and shipping

Both are adapters, chosen by environment variable. Nothing about them leaks
into the checkout UI.

### Payments — `PAYMENT_PROVIDERS`

- **`cod`** — cash on delivery. Works immediately, no account needed.
- **`bank_transfer`** — shows your account details and waits; staff confirm the
  transfer from the order page. Set `BANK_TRANSFER_INSTRUCTIONS`.
- **`stripe`** — hosted Stripe Checkout, so card data never touches this server.
  Set `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`.

An order is confirmed by the Stripe **webhook**, not by the browser returning —
a customer who closes the tab after paying still gets their glasses. Test
locally with:

```bash
stripe listen --forward-to localhost:3000/api/webhooks/stripe
```

Adding a provider means one adapter function in `src/lib/payments.ts` plus an
entry in `ALL_METHODS`.

### Shipping — `SHIPPING_PROVIDER`

- **`table_rate`** (default) — rates from the `ShippingRate` table. No account.
- **`shippo`** — live carrier rates and printable labels. Set `SHIPPO_API_KEY`.
- **`easypost`** — live rates. Set `EASYPOST_API_KEY`.

Live providers fall back to the rate table if the key is missing or the API
call fails, so a carrier outage degrades to flat-rate instead of blocking
checkout.

### Image storage — `STORAGE_DRIVER`

`local` writes to `/public/uploads` (default, zero setup). `s3` covers S3,
Cloudflare R2 and DigitalOcean Spaces — set the `S3_*` variables and
`npm install @aws-sdk/client-s3`.

## Patient data

This is health data, and the app treats it that way:

- Every customer gets a **patient file** with a sequential number (`P-000001`).
  Guests get one too — an optical order can't be remade or followed up without
  one. A returning guest is matched on email rather than getting a new file.
- **Prescriptions are versioned.** A new one never overwrites an old one, and
  each order line stores its own immutable snapshot, so an invoice from three
  years ago still reads correctly.
- Customer-entered prescriptions land as `pending_verification` and appear in
  the optician's queue. The lab ticket refuses to look ready until verified.
- Diopter fields are dropdowns stepping in 0.25 D. Cylinder without an axis is
  rejected. A free-text box is how a lab ends up cutting −2.13.
- Every write to a patient record, price or order is written to `AuditLog` with
  the actor and IP. Clinical values are deliberately kept *out* of the log
  detail — the log is read far more widely than the record it describes.
- CSV exports of patient data are themselves audited.
- `Patient` carries `consentMarketing`, `consentDataAt`, `consentVersion`,
  `retentionUntil` and a `deletedAt` soft delete, ready for whatever retention
  policy you adopt.

**Before going live** you should add: encryption at rest on the database, a
documented retention period, and a customer-facing route for correction and
erasure requests. The data model supports all three; the policy decisions are
yours.

### Two rules worth keeping

**Money is always an integer of minor units** (paisa, cents). Staff type major
units in forms; conversion happens once, at the edge. No float arithmetic on
prices anywhere.

**Prices are never computed in a component.** `src/lib/pricing.ts` re-prices
the cart from the database on every read, so a tampered client payload cannot
change what is charged, and a price or stock change is reflected the moment the
customer looks at their bag.

## Going to production

1. **Postgres.** Change `provider` in `prisma/schema.prisma` to `postgresql`,
   point `DATABASE_URL` at it, then `npx prisma migrate deploy`. The schema
   avoids enums, arrays and native JSON precisely so this needs no other edits.
2. **Secrets.** A fresh `AUTH_SECRET`. New staff passwords. Real payment keys.
3. **`NEXT_PUBLIC_APP_URL`** must be the public URL — Stripe's return links use it.
4. **Storage.** Move to `s3` unless the server has durable, backed-up disk.
5. **Stripe webhook.** Point it at `/api/webhooks/stripe` and set the signing secret.
6. **Tax.** `TAX_RATE_BPS` in basis points (1700 = 17%), `TAX_INCLUSIVE` if
   displayed prices already contain it.

### Not built yet

Honest list of what a production launch still needs:

- **Transactional email.** `MAIL_DRIVER` is read from the environment but no
  sender is wired up — order confirmations are not actually sent. Add a
  provider and call it from `placeOrderAction` and the Stripe webhook.
- **Password reset.** There is no forgotten-password flow.
- **Rate limiting** on login and the upload endpoints.
- **Automated tests.** The geometry in `src/lib/tryon.ts` and the promotion
  engine in `src/lib/promotions.ts` are pure and are the obvious first targets.
